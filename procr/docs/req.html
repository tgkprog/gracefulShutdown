Transaction Processor API (PROCR) - Requirements Specification

Project: Transaction Processor Service (PROCR)
Technology Stack: Java Spring Boot REST API
Document Version: 1.0
Last Updated: October 22, 2026

1. Overview

The PROCR (Processor) service is a stateless Spring Boot REST API that processes transaction requests from Adapter services. It receives YAML-formatted transaction data via HTTP POST requests, performs random approval decisions (99% success rate), and returns structured approval/rejection responses. The service is transaction-agnostic and does not persist any data.

2. Core Architecture

REQ-ARC-001: Stateless Design
  • The service shall have NO database or persistent storage
  • Each request is processed independently with no session or state management
  • All transaction data is transient; only logging is maintained
  • Multiple instances can run in parallel without coordination
REQ-ARC-002: Service Endpoints
The service shall expose two REST API endpoints:
  • /health - Health check endpoint (GET)
  • /process - Transaction processing endpoint (POST)

3. Health Check Endpoint

REQ-HEALTH-001: Health Endpoint Specification
  • Path: /health
  • Method: GET
  • Authentication: None
  • Response Status: 200 OK
REQ-HEALTH-002: Health Response Format
The health endpoint shall return a YAML response indicating service status.
status: UP service: PROCR timestamp: "2026-10-22T23:17:46.602+05:30" uptime_seconds: 3600 version: "1.0.0"
Note: The health endpoint requires no authentication and should respond quickly. It can be used by Adapters to verify that PROCR is available before sending transaction requests.

4. Transaction Processing Endpoint

REQ-PROC-001: Process Endpoint Specification
  • Path: /process
  • Method: POST
  • Content-Type (Request): application/x-yaml
  • Content-Type (Response): application/x-yaml
  • Authentication: None
REQ-PROC-002: Input Format - YAML Transaction
The endpoint accepts YAML-formatted transaction data from the Adapter. The YAML structure shall contain transaction details received from Central.
# Input YAML Example txn_id: TXN-001234 stan: "123456" txn_type: "T1" narration: "Purchase of Office Supplies" quantity: 5 rate: 99.99 taxes: 49.99 total: 549.89 timestamp: "2026-10-22T23:17:46.602+05:30"
REQ-PROC-003: Input Validation
  • All required fields must be present in the YAML request
  • If any required field is missing or malformed, return HTTP 400 Bad Request with error details
  • Field validation errors shall be logged with the request details
  • Do not process invalid requests

5. Processing Logic

REQ-PROC-LOGIC-001: Approval Decision Algorithm
  • Generate a random number between 1-100 (inclusive)
  • If random number is 1-99: APPROVE the transaction (99% success rate)
  • If random number is 100: REJECT the transaction (1% rejection rate)
  • All decisions are final and deterministic for a single request
  • Response Delay Before Sending:
    • Processing Flow: Log decision → Calculate sleep duration → Sleep → Log sleep action → Send response
    • Sleep Duration Formula: sleep_ms = fixed_delay + random_value
      • fixed_delay: Base delay in milliseconds (always applied)
      • random_value: Random value selected from range [min_random, max_random] in steps of step
    • Example: If fixed=1000, min_random=100, step=100, max_random=1000:
      • Possible random values: 100, 200, 300, 400, 500, 600, 700, 800, 900, 1000
      • Sleep duration: 1000 + {one of above} = 1100 to 2000 ms
    • Default Configuration:
      • fixed_delay = 0 ms
      • min_random = 0 ms
      • step = 100 ms
      • max_random = 200 ms
      • Default sleep range: 0 to 200 ms (in 100 ms increments)
    • Configurability: All parameters (fixed, min_random, step, max_random) should be configurable via application.properties
    • Logging: Processor must log the calculated sleep duration before and after sleeping
REQ-PROC-LOGIC-002: Rejection Reasons
When a transaction is REJECTED, randomly select one of the following failure reasons:
  • Insufficient Funds
  • Card Closed
  • Network Down
Each rejection reason should have equal probability (33.3% each).
REQ-PROC-LOGIC-003: Processing Determinism
  • Each request is processed independently
  • No state carries over between requests
  • No transaction history is maintained
  • Concurrent requests may have different outcomes based on random generation

6. Response Format

REQ-RESPONSE-001: Success Response (HTTP 200)
When a transaction is processed successfully (regardless of approval/rejection), the endpoint shall return HTTP 200 OK with the following YAML structure:
Example - APPROVED Transaction:
txn_id: TXN-001234 stan: "123456" status: APPROVED reason: null date: "2026-10-22T23:17:46.602+05:30" timestamp: "2026-10-22T23:17:46.602+05:30" response_time_ms: 45
Example - REJECTED Transaction:
txn_id: TXN-001235 stan: "654321" status: REJECTED reason: Insufficient Funds date: "2026-10-22T23:17:46.602+05:30" timestamp: "2026-10-22T23:17:46.602+05:30" response_time_ms: 52
Field Data Type Description Notes
txn_id String Transaction ID from input (TXN-XXXXX) Echo from request
stan String System Trace Audit Number Echo from request
status String (Enum) Transaction approval status APPROVED or REJECTED
reason String or null Failure reason if rejected null for APPROVED, one of: "Insufficient Funds", "Card Closed", "Network Down" for REJECTED
date DateTime Processing completion timestamp ISO 8601 format
timestamp DateTime Processing completion timestamp (duplicate for compatibility) ISO 8601 format, same as date
response_time_ms Integer Time taken to process request In milliseconds
REQ-RESPONSE-002: Error Response (HTTP 400)
When a request contains invalid or malformed data, return HTTP 400 Bad Request with error details in YAML format:
error: Invalid request message: Missing required field: txn_id timestamp: "2026-10-22T23:17:46.602+05:30" status: 400
REQ-RESPONSE-003: Server Error Response (HTTP 500)
When an unexpected server error occurs, return HTTP 500 Internal Server Error with error details in YAML format:
error: Internal server error message: Unexpected error processing transaction timestamp: "2026-10-22T23:17:46.602+05:30" status: 500

7. Logging Requirements

REQ-LOG-001: Request Logging
For each incoming transaction request, log:
  • Request timestamp
  • Transaction ID
  • STAN
  • Transaction type and narration
  • Request size and format
[2026-10-22T23:17:46.602+05:30] INFO TransactionProcessor - Received TXN-001234 (STAN: 123456, T1: Purchase of Office Supplies)
REQ-LOG-002: Processing Logging
For each transaction processed, log:
  • Decision timestamp
  • Approval/Rejection status
  • Rejection reason (if applicable)
  • Processing time in milliseconds
[2026-10-22T23:17:46.602+05:30] INFO TransactionProcessor - TXN-001234 APPROVED (52ms) [2026-10-22T23:17:46.603+05:30] INFO TransactionProcessor - TXN-001235 REJECTED - Insufficient Funds (45ms)
REQ-LOG-003: Error Logging
For validation errors or processing failures, log:
  • Error level (ERROR or WARN)
  • Error description
  • Request details (if available)
  • Stack trace (for exceptions)
[2026-10-22T23:17:46.602+05:30] WARN TransactionProcessor - Invalid YAML format: missing field 'txn_id' [2026-10-22T23:17:46.602+05:30] ERROR TransactionProcessor - Exception processing TXN-001236: ...
REQ-LOG-004: Health Check Logging
  • Log health check requests at DEBUG level (optional, to reduce log volume)
  • Log health check failures at ERROR level
  • Include service uptime and request count in periodic logs

8. Performance Requirements

REQ-PERF-001: Response Time
  • Health check endpoint should respond in <100ms
  • Transaction processing should complete in <200ms per transaction
  • Actual response time depends on YAML parsing and JSON serialization
REQ-PERF-002: Throughput
  • The service shall support at least 100 concurrent transaction requests
  • Stateless design allows horizontal scaling (multiple instances)
  • No database connection pooling or resource contention

9. Configuration Requirements

REQ-CFG-001: Application Properties
The following properties shall be configurable via application.properties or environment variables:
Property Default Value Description
server.port 8080 HTTP server port
server.servlet.context-path / Application context path
procr.approval.rate 99 Approval rate as percentage (1-100)
logging.level.root INFO Root logging level
spring.application.name procr Application name

10. Error Handling

REQ-ERR-001: Malformed YAML
  • If YAML is malformed or cannot be parsed, return HTTP 400 with error message
  • Log the parsing error with the request body (truncated for security)
  • Do not crash the service; continue processing subsequent requests
REQ-ERR-002: Missing Required Fields
Required fields in the YAML request:
  • txn_id
  • stan
  • txn_type
  • narration
  • quantity
  • rate
  • total
If any are missing, return HTTP 400 with field name in error message.
REQ-ERR-003: Unexpected Exceptions
  • Catch all unexpected exceptions in the processing pipeline
  • Return HTTP 500 with generic error message
  • Log the full exception stack trace for debugging
  • Do not expose sensitive information in error responses

11. Integration with Adapter

REQ-INTEG-001: HTTP Request from Adapter
The Adapter will make HTTP POST requests to the /process endpoint:
  • URL: http://procr-host:8080/process
  • Method: POST
  • Content-Type: application/x-yaml
  • Body: YAML-formatted transaction
  • Timeout: Adapter should set a reasonable timeout (suggest 5-10 seconds)
REQ-INTEG-002: Response Handling
The Adapter will:
  • Parse the JSON response from /process
  • Extract approval status and reason (if rejected)
  • Transform the response back to JSON format for Central
  • Send the response to Central via the TCP connection
  • Handle HTTP errors (4xx, 5xx) by logging and potentially retrying

12. Deployment Considerations

REQ-DEPLOY-001: Containerization
  • Application should be containerizable (Docker-ready)
  • No external dependencies beyond JDK and Spring Boot
  • Environment variables for configuration (PROCR_PORT, PROCR_APPROVAL_RATE, etc.)
REQ-DEPLOY-002: Graceful Shutdown
  • Application should handle SIGTERM gracefully
  • Allow in-flight requests to complete within a timeout period
  • Flush logs before shutdown
  • Exit cleanly with status code 0

13. Security Considerations

REQ-SEC-001: Input Validation
  • Validate YAML structure and field types
  • Reject requests with unexpected fields or data types
  • Do not allow arbitrary code execution from YAML
  • Use safe YAML parsing libraries
REQ-SEC-002: No Sensitive Data Logging
  • Do not log full transaction amounts or sensitive card information
  • Log only transaction IDs, STANs, and processing results
  • Truncate long field values in logs
REQ-SEC-003: No Authentication (For Now)
  • This specification does not include authentication/authorization
  • Assume trusted network between Adapter and PROCR
  • Future versions may add API keys or OAuth2

14. Summary of API Contract

Endpoint Method Request Format Response Format Status Codes
/health GET N/A application/x-yaml 200 OK
/process POST application/x-yaml application/x-yaml 200 OK, 400 Bad Request, 500 Internal Server Error
Key Points for Implementation:
  • Completely stateless - no caching, sessions, or database
  • 99% approval rate is deterministic random decision per request
  • 3 possible rejection reasons with equal probability
  • All processing logged but no data persistence
  • All responses in YAML format: Both health and process endpoints return YAML
  • Simple synchronous request/response model
