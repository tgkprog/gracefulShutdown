PROCR Service - Implementation Guide

Clear explanation of all processing requirements, with focus on "Response Delay Before Sending"

1. Processing Overview

The PROCR service receives transactions from Central, processes them with a random approval decision, applies a configurable delay, logs the actions, and sends a response back.

Request Received (from Central) ↓ Generate Random Approval Decision (1-100) ↓ Log Decision ↓ Calculate Sleep Duration ↓ Log Calculated Delay ↓ Sleep for Calculated Duration ↓ Log Sleep Completion ↓ Send Response to Central

2. Approval Decision Algorithm (REQ-PROC-LOGIC-001)

Step 1: Generate Random Decision

  • Generate a random integer from 1 to 100 (inclusive)
  • If 1-99: Decision = APPROVE (99% success rate)
  • If 100: Decision = REJECT (1% rejection rate)
  • Decision is deterministic for a single request (no change once made)
Example:
  • Random = 45 → APPROVE (success)
  • Random = 100 → REJECT (failure)
  • Random = 1 → APPROVE (success)

3. Response Delay Before Sending (NEW - CLARIFIED)

Purpose: Simulate real-world processing delays. The processor will wait before responding to simulate network latency or backend processing time.

Sleep Duration Formula

sleep_ms = fixed_delay + random_value

Where:

  • fixed_delay: Base delay applied to every response (in milliseconds)
  • random_value: Additional random delay selected from a range (in milliseconds)

Random Value Calculation

The random value is generated from a set of equally-spaced values:

Possible values: [min_random, min_random+step, min_random+2*step, ..., max_random]

Parameters:

  • min_random: Minimum random value (in milliseconds)
  • step: Increment between possible values (in milliseconds)
  • max_random: Maximum random value (in milliseconds)

Concrete Example #1: Default Configuration

Parameter Value Description
fixed_delay 0 ms No base delay
min_random 0 ms Random starts from 0
step 100 ms Increment by 100ms each
max_random 200 ms Random goes up to 200

Calculation:

Possible random values: [0, 100, 200] (starts at 0, increments by 100, stops at 200) Processor randomly selects one: - 0 ms (33% chance) - 100 ms (33% chance) - 200 ms (33% chance) Total sleep = 0 (fixed) + {0 or 100 or 200} (random) = 0, 100, or 200 ms (equal probability)

Concrete Example #2: Custom Configuration

Parameter Value Description
fixed_delay 1000 ms Always wait 1 second first
min_random 100 ms Random starts from 100
step 100 ms Increment by 100ms each
max_random 1000 ms Random goes up to 1000

Calculation:

Possible random values: [100, 200, 300, 400, 500, 600, 700, 800, 900, 1000] (starts at 100, increments by 100, stops at 1000) Processor randomly selects one (10% each): - 100 ms - 200 ms - 300 ms - ... (continues) - 1000 ms Total sleep = 1000 (fixed) + {100 to 1000 in steps of 100} (random) = 1100 to 2000 ms (10 possible values, equal probability)

4. Logging Requirements

The processor must log at multiple stages:

1. Log the approval decision (APPROVE or REJECT) 2. Log the calculated sleep duration (e.g., "Sleeping for 150 ms") 3. Log sleep completion (e.g., "Sleep completed after 150 ms") 4. Log the response being sent

Example Log Output:

[2024-10-23 12:34:56] Processing transaction TXN-123456 [2024-10-23 12:34:56] Decision: APPROVE (random=45) [2024-10-23 12:34:56] Calculated sleep duration: 150 ms [2024-10-23 12:34:56] Starting sleep... [2024-10-23 12:34:56] Sleep completed after 150 ms [2024-10-23 12:34:56] Sending APPROVE response to Central

5. Configuration via application.properties

All delay parameters should be configurable:

# Response Delay Configuration (in milliseconds) procr.response.delay.fixed=0 procr.response.delay.min_random=0 procr.response.delay.step=100 procr.response.delay.max_random=200

Notes:

  • All values are in milliseconds
  • Set fixed=0 for no base delay
  • Set min_random=max_random=0 to disable random delay entirely
  • step must be a positive integer dividing the range evenly

6. Rejection Reasons (REQ-PROC-LOGIC-002)

When a transaction is REJECTED (random = 100), select one of these reasons with equal probability:

Reason Probability Meaning
Insufficient Funds 33.3% Account balance too low
Card Closed 33.3% Card is no longer valid
Network Down 33.3% Temporary network issue
Example Rejection:
  • Random = 100 → REJECT
  • Random reason selector = 2 → "Card Closed"
  • Log: "Decision: REJECT (reason: Card Closed)"

7. Response Format

Success Response (APPROVE)

response_type: APPROVE txn_id: TXN-123456 status: SUCCESS message: Transaction approved successfully timestamp: 2024-10-23T12:34:56Z

Failure Response (REJECT)

response_type: REJECT txn_id: TXN-123456 status: FAILED reason: Card Closed message: Transaction rejected - Card Closed timestamp: 2024-10-23T12:34:56Z

8. Processing Determinism (REQ-PROC-LOGIC-003)

  • No State: Each request is processed independently
  • No History: No transaction history is maintained
  • Independent: Concurrent requests have independent outcomes
  • Deterministic: Same random seed produces same results (if needed for testing)
Important: Each time PROCR receives a request for the same transaction, it will generate a NEW random decision. There is no caching or state preservation between requests.

9. API Endpoints

GET /health

Purpose: Health check (returns YAML)

Request: GET /health Response: 200 OK Content-Type: application/x-yaml status: UP version: 1.0.0 timestamp: 2024-10-23T12:34:56Z

POST /process

Purpose: Process a transaction

Request: POST /process Content-Type: application/x-yaml txn_id: TXN-123456 stan: "123456" type: T1 narration: "Payment received" quantity: 50 rate: 25.50 taxes: 127.50 total: 1402.50 Response: 200 OK Content-Type: application/x-yaml response_type: APPROVE txn_id: TXN-123456 status: SUCCESS message: Transaction approved successfully timestamp: 2024-10-23T12:34:56Z

10. Implementation Checklist

  • ☐ Receive YAML transaction from Central on /process endpoint

  • ☐ Log the decision (APPROVE or REJECT)
  • ☐ Calculate sleep duration using formula: fixed + random_value
  • ☐ Log the calculated sleep duration
  • ☐ Sleep for the calculated duration
  • ☐ Log sleep completion
  • ☐ If REJECT, select one rejection reason (33.3% each)
  • ☐ Construct response in YAML format
  • ☐ Log the response being sent
  • ☐ Send response back to Central
  • ☐ Make all delay parameters configurable via application.properties
  • ☐ Implement /health endpoint (returns YAML)
  • ☐ Handle concurrent requests independently
