Transaction Server Application - Requirements Specification

Project: Central Transaction Server
Technology Stack: Java Spring Boot TCP Socket
Document Version: 1.0
Last Updated: October 22, 2026

1. Overview

The application shall be a Java Spring Boot server that accepts TCP socket connections from a single client at a time. The server will send transaction messages to the connected client and receive transaction acknowledgments. The server manages session lifecycle (session start/end) and maintains transaction queues during active sessions.

2. Network Architecture

REQ-NET-001: TCP Port Listening
The application shall listen on a configurable TCP port (default: 5000 or configurable via application properties). The server shall accept incoming TCP socket connections.
REQ-NET-002: Single Client Connection
The server shall accept and maintain only ONE active client connection at any given time. If a new connection attempt arrives while a client is already connected, the new connection shall be rejected or queued.
REQ-NET-003: Graceful Disconnection Handling
Upon client disconnection or connection termination:
  • All pending transactions shall be immediately dropped (no persistence or retry)
  • All session state shall be cleared
  • The server shall be ready to accept a new connection
  • The next client connection must explicitly send a new SESSION_START message

3. Threading Architecture

REQ-THREAD-001: Thread Pool Design
The server shall use a queue-based multi-threaded architecture to safely decouple transaction generation, transmission, and response handling:
  • Sender Pool (2 threads): Generate transactions and publish to OutgoingQueue
  • TCP Writer (1 thread): Read from OutgoingQueue and write to TCP socket
  • TCP Reader (1 thread): Read from TCP socket and publish to IncomingQueue
  • Receiver Pool (2 threads): Process acknowledgments from IncomingQueue and update cache
  • Shared Cache: Thread-safe in-memory store for pending transactions (key: txn_id, value: txn details)

REQ-THREAD-002: Sender Pool Behavior
  • Two sender threads work independently to generate transactions
  • Each sender respects the session state (active/inactive)
  • Senders publish generated transactions to OutgoingQueue (thread-safe blocking queue)
  • Senders also store transaction in shared Cache with TTL (default: 9 seconds)
  • If OutgoingQueue is full, senders block until space is available (backpressure)
REQ-THREAD-003: TCP Writer Thread Behavior
  • Single TCP writer ensures no concurrent writes to socket (thread-safe)
  • Blocks on OutgoingQueue waiting for transactions
  • Upon receiving transaction: serialize to JSON and write to TCP socket
  • Each message ends with newline for line-based parsing by Adapter
  • Handle network errors: close socket, log error, transition to DISCONNECTED state
REQ-THREAD-004: TCP Reader Thread Behavior
  • Single TCP reader ensures no concurrent reads from socket (thread-safe)
  • Blocks on socket read waiting for acknowledgments (from Adapter in JSON format)
  • Upon receiving acknowledgment: deserialize JSON and publish to IncomingQueue
  • Adapter converts PROCR YAML responses back to JSON for Central to consume
  • Handle network errors: close socket, log error, transition to DISCONNECTED state
REQ-THREAD-005: Receiver Pool Behavior
  • Two receiver threads process acknowledgments independently
  • Receivers block on IncomingQueue waiting for acknowledgments
  • Upon receiving acknowledgment: update cache to mark transaction as acknowledged
  • Log the acknowledgment with timestamp and transaction details
  • Remove transaction from cache (cleanup)
REQ-THREAD-006: Shared Cache Management
  • Cache implementation: ConcurrentHashMap or similar thread-safe map
  • Key: txn_id (String), Value: Transaction object + timestamp
  • TTL enforcement: Background cleanup task removes entries older than 9 seconds
  • TTL timeout indicates adapter did not respond within timeout window
  • On disconnect: clear all pending transactions from cache
REQ-THREAD-007: Queue Specifications
  • OutgoingQueue: BlockingQueue<Transaction>, capacity: 100 (configurable)
  • IncomingQueue: BlockingQueue<Acknowledgment>, capacity: 100 (configurable)
  • Both queues use fair FIFO ordering
  • Queues automatically cleared on SESSION_END → DISCONNECTED transition

4. Message Protocol

3.1 Message Types

Message Type Direction Description
SESSION_START Client → Server Initiates a session; server starts sending transactions
SESSION_END Client → Server Terminates a session; server stops sending new transactions but waits for pending acknowledgments
TRANSACTION Server → Client Sends a transaction with complete details (see Section 3.3)
TXN_ACKNOWLEDGE Client → Server Acknowledgment of received transaction

3.2 Session Management

REQ-MSG-001: Session Start
When client sends SESSION_START message:
  • Server shall transition to ACTIVE session state
  • Server shall begin sending transactions (as per Section 4)
  • Server shall log session start event with timestamp
REQ-MSG-002: Session End
When client sends SESSION_END message:
  • Server shall transition to INACTIVE session state
  • Server shall STOP sending new transactions immediately
  • Server shall CONTINUE waiting for acknowledgments of previously sent transactions
  • Server shall log session end event with timestamp
  • All received transaction acknowledgments shall still be logged
REQ-MSG-003: Transaction Lifecycle with Disconnection
  • During ACTIVE session: Server sends transactions and waits for acknowledgments
  • After SESSION_END but before disconnection: Server waits for pending transaction acknowledgments
  • Upon connection loss: All remaining pending transactions are immediately discarded

3.3 Transaction Message Format

REQ-MSG-004: Transaction Message Structure
Each transaction message shall contain the following fields:
Field Data Type Description Format/Constraints
Message ID String Unique identifier for this transaction (TXN number) Alphanumeric, e.g., "TXN-001234"
STAN String System Trace Audit Number 6-12 digit numeric string
Transaction Type String (Enum) Type of transaction One of: T1, T2, S1
Narration String Transaction description Sensible, pre-defined per transaction type (see Section 3.4)
Quantity Integer Number of items Positive integer, e.g., 1-100
Rate Decimal Price per unit Decimal with 2 decimal places, e.g., 99.99
Taxes Decimal Tax amount (10% fixed) Calculated as: (Quantity × Rate) × 0.10
Total Decimal Total amount Calculated as: (Quantity × Rate) + Taxes
Timestamp DateTime Transaction creation time ISO 8601 format, e.g., "2026-10-22T23:08:41Z"

3.4 Narration Pool

REQ-MSG-005: Pre-defined Narrations
The server shall maintain a pool of pre-defined narrations for each transaction type. For each transaction, the server shall randomly select one narration from the corresponding type pool.
Transaction Type Narrations (Pick one randomly)
T1 Purchase of Office Supplies Sales Order Fulfillment Inventory Replenishment - Books
T2 Software License Renewal Hardware Maintenance Contract Professional Consultation Services
S1 Customer Refund Processing Payment for Returned Merchandise Settlement of Service Credit

5. Transaction Generation and Timing

REQ-TXN-001: Transaction Generation Rate
  • The server shall generate and send 4 transactions every 10 seconds (400 ms per transaction on average)
  • Transactions shall be RANDOMLY distributed across the 10-second window (not evenly spaced)
  • Each transaction shall be sent only when a session is ACTIVE
  • No transactions shall be sent after SESSION_END is received until a new SESSION_START arrives
REQ-TXN-002: Random Timing Implementation
  • Calculate a random delay between 0-10000 milliseconds at the start of each 10-second window
  • Send transactions at random intervals within this window
  • Ensure 4 transactions fit within the window with appropriate spacing
  • Example: Send at T=150ms, T=2400ms, T=5800ms, T=8300ms
REQ-TXN-003: Transaction Data Randomization
For each transaction:
  • Randomly select a transaction type (T1, T2, or S1) with equal probability (33.3% each)
  • Randomly select a narration from the 3 narrations for the chosen type
  • Generate a random STAN (6-12 digit string)
  • Generate a random Quantity (1-100)
  • Generate a random Rate (10.00-999.99)
  • Calculate Taxes as: (Quantity × Rate) × 0.10
  • Calculate Total as: (Quantity × Rate) + Taxes
  • Assign sequential TXN number (TXN-001, TXN-002, etc.)

6. Transaction Acknowledgment Flow

REQ-ACK-001: Acknowledgment Processing
Upon receiving a TXN_ACKNOWLEDGE message from the client:
  • Server shall log the acknowledgment with transaction ID and timestamp
  • Server shall record the acknowledgment status (received/processed)
  • No persistence or special handling is required; acknowledgment is for logging only
REQ-ACK-002: Acknowledgment Wait Period
  • After SESSION_END is received, the server shall continue accepting and logging acknowledgments
  • Server shall wait indefinitely for acknowledgments of sent transactions (until connection closes)
  • No timeout mechanism for acknowledgments is required
  • Upon connection loss, all unacknowledged transactions are immediately discarded

7. Logging and Monitoring

REQ-LOG-001: Event Logging
The server shall log the following events:
  • Server Startup: Application started, listening on port [PORT]
  • Client Connected: Client connection established from [IP:PORT]
  • Session Start: SESSION_START received at [TIMESTAMP]
  • Transaction Sent: TXN-[ID] sent to client (Type: [TYPE], STAN: [STAN], Amount: [TOTAL])
  • Acknowledgment Received: TXN_ACK received for TXN-[ID] at [TIMESTAMP]
  • Session End: SESSION_END received at [TIMESTAMP], waiting for pending acknowledgments
  • Client Disconnected: Connection closed, [N] pending transactions dropped
  • New Session Ready: Server ready to accept new connection and SESSION_START
REQ-LOG-002: Log Format
All logs shall include:
  • Timestamp (ISO 8601 format)
  • Log Level (INFO, WARN, ERROR)
  • Component/Class name
  • Message with relevant context
Example: [2026-10-22T23:08:41.400+05:30] INFO TransactionService - TXN-001234 sent (T1, STAN: 123456, Amount: 1100.00)

8. Application State Machine

Server State Transitions:

DISCONNECTED
└─ (Client connects)
    ↓
CONNECTED (Waiting for SESSION_START)
└─ (Receive SESSION_START)
    ↓
ACTIVE (Sending Transactions)
└─ (Receive SESSION_END)
    ↓
INACTIVE (Waiting for Acknowledgments)
└─ (Client disconnects)
    ↓
DISCONNECTED

9. Error Handling and Edge Cases

REQ-ERR-001: Malformed Messages
  • If a message received from the client is malformed or unrecognized, log a warning and ignore it
  • Do not crash the server; maintain the connection
REQ-ERR-002: Session Start During Active Session
  • If SESSION_START is received while a session is already ACTIVE, log a warning and ignore it
  • Continue with the current active session
REQ-ERR-003: Socket Read/Write Errors
  • If any I/O error occurs during socket communication, immediately close the connection
  • Log the error and transition to DISCONNECTED state
  • Drop all pending transactions
  • Prepare for a new client connection

10. Configuration Requirements

REQ-CFG-001: Application Properties
The following properties shall be configurable via application.properties or environment variables:
  • server.port: TCP port number (default: 5000)
  • txn.rate.interval: Interval between transaction batches in milliseconds (default: 10000)
  • txn.rate.count: Number of transactions per batch (default: 4)
  • txn.batch.random: Enable random spacing within batch (default: true)

11. Performance and Scalability

REQ-PERF-001: Thread Pool Sizing
  • Sender Pool: 2 threads (configurable)
  • TCP Writer: 1 dedicated thread
  • TCP Reader: 1 dedicated thread
  • Receiver Pool: 2 threads (configurable)
  • Total: 6 threads minimum for baseline operation
  • Thread pool size adjustable via configuration for different load profiles
REQ-PERF-002: Memory Efficiency
  • Pending transactions held in shared cache (ConcurrentHashMap)
  • Queue capacity: 100 per queue (configurable)
  • TTL-based cleanup: transactions expire after 9 seconds
  • Upon disconnection: all queues and cache cleared immediately
  • No long-term storage of transaction history required
REQ-PERF-003: Backpressure Handling
  • Sender threads block if OutgoingQueue reaches capacity
  • This natural backpressure prevents memory exhaustion
  • Receiver threads block if IncomingQueue is empty
  • Non-blocking I/O handled by dedicated TCP threads

12. Testing Considerations

Testing Strategy (Not a formal requirement, but recommended):
  • Unit Tests: Test transaction generation logic, rate calculation, narration selection
  • Integration Tests: Test socket communication, session lifecycle, message parsing
  • Manual Testing: Use telnet or a custom client to verify protocol compliance
  • Load Testing: Verify correct behavior with continuous connection/disconnection cycles

13. Non-Functional Requirements

REQ-NFR-001: Reliability
The application shall not lose transaction acknowledgments that have been sent by the client before disconnection. Once an acknowledgment is received, it shall be logged and shall not be lost.
REQ-NFR-002: Graceful Shutdown
When the Spring Boot application is shut down:
  • The active client connection (if any) shall be closed gracefully
  • All pending transactions shall be discarded
  • All logs shall be flushed
  • Application shall exit cleanly
REQ-NFR-003: Code Quality
  • Follow Spring Boot best practices and conventions
  • Use dependency injection for service components
  • Implement proper exception handling
  • Include JavaDoc comments for public APIs
  • Use meaningful class and method names

14. Summary of Key Behaviors

Scenario Expected Behavior
Client connects Server accepts connection, logs event, waits for SESSION_START
Client sends SESSION_START Server transitions to ACTIVE, begins sending transactions every 10 seconds (4 txns with random spacing)
Server sends transaction Server logs transaction details (TXN ID, STAN, Type, Amount) and waits for acknowledgment
Client sends TXN_ACKNOWLEDGE Server logs acknowledgment, continues sending transactions
Client sends SESSION_END Server stops sending new transactions, continues waiting for pending acknowledgments
All acknowledgments received (after SESSION_END) Server remains idle, ready for client to send new SESSION_START or close connection
Client disconnects Server drops all pending transactions, clears session state, logs event, waits for new connection
New client connects Process repeats from beginning; new client must send SESSION_START
