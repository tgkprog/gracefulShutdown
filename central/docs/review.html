1. Architecture Overview

The Central Server implements a multi-threaded transaction distribution system with 6 concurrent execution threads:

Component Type Count Responsibility
Sender Threads Executor Pool 2 Generate transactions respecting session state and timing windows
Receiver Threads Executor Pool 2 Process acknowledgments and update cache
TCP Writer Single Thread 1 Serialize transactions to YAML and send via socket (no concurrent writes)
TCP Reader Single Thread 1 Read YAML from socket and route messages (session, acknowledgments)

3. State Machine Behavior

State Transitions From Transitions To Sender Behavior Receiver Behavior
DISCONNECTED Initial, SESSION_END_REQUESTED CONNECTED No transactions Stopped
CONNECTED DISCONNECTED ACTIVE Wait for SESSION_START Ready but waiting
ACTIVE CONNECTED SESSION_END_REQUESTED Generate transactions Process ACKs
SESSION_END_REQUESTED ACTIVE DISCONNECTED Stop generating, drain cache Continue processing ACKs

4. Answer to Original Questions

Question 1: Connection without SESSION_START

Answer: YES, correctly handled ✓

If a client connects but does not send SESSION_START:

  • SessionManager stays in CONNECTED state
  • SenderThreadPool.senderLoop() checks sessionManager.isActive() and sleeps 100ms repeatedly
  • No transactions are generated
  • ReceiverThreadPool continuously waits for acknowledgments (none arrive)

Result: Connection is maintained, no transactions sent, clean idle state.

Question 2: SESSION_START then SESSION_END

Answer: YES, correctly handled ✓

Sequence of events:

  1. Client sends SESSION_START → SessionManager transitions to ACTIVE
  2. SenderThreadPool generates and sends transactions
  3. Client sends SESSION_END → SessionManager transitions to SESSION_END_REQUESTED
  4. SenderThreadPool.senderLoop() detects SESSION_END_REQUESTED and breaks
  5. ReceiverThreadPool continues processing acknowledgments for in-flight transactions
  6. TransactionCache holds entries for 9 seconds (TTL) to match acknowledgments
  7. Connection closes → SessionManager transitions to DISCONNECTED

Result: No new transactions sent after SESSION_END, but pending ACKs are processed.

5. Threading Model

Sender Pool (2 threads)

while (sessionMgr.isActive() && !interrupted) {
    if (state == SESSION_END_REQUESTED) break;
    
    for (int i = 0; i < rateCount; i++) {
        Transaction txn = generator.generate();
        TxnData data = new TxnData(txn, sequenceNum++);
        outgoingQueue.put(data);  // BlockingQueue, thread-safe
    }
    
    Thread.sleep(random delay within interval);
}

Receiver Pool (2 threads)

while (running && !interrupted) {
    try {
        AckData ack = incomingQueue.take();  // Blocks until available
        transactionCache.remove(ack.getTxnId());
        logger.info("Received ACK for {}", ack.getTxnId());
    } catch (InterruptedException e) {
        break;
    }
}

TCP Writer Thread (single, no concurrent writes)

while (running) {
    TxnData data = outgoingQueue.take();
    String yaml = serializer.toYaml(data.getTransaction());
    socketOutput.write((yaml + "\n---\n").getBytes());
    socketOutput.flush();
}

TCP Reader Thread (YAML parser with "---" delimiter)

while (running) {
    line = reader.readLine();
    if (line == null) break;  // Connection closed
    
    if (line.equals("---")) {
        String yaml = messageBuilder.toString();
        handleMessage(yaml);  // Route to session mgr or incoming queue
        messageBuilder = new StringBuilder();
    } else {
        messageBuilder.append(line + "\n");
    }
}

8. Key Design Decisions

  • Single TCP Writer: Prevents socket corruption from concurrent writes. All transactions serialized sequentially by one thread.
  • Single TCP Reader: All incoming messages (SESSION_START/END, TXN_ACKNOWLEDGE) handled by one thread, routed to appropriate queues.
  • Separate Pools: Sender and Receiver pools are independent, decoupled via thread-safe BlockingQueues.
  • State Machine: AtomicReference ensures thread-safe transitions; used by both senders and readers.
  • Message Delimiters: YAML messages separated by "---" on its own line, enabling line-by-line reading without buffering entire messages.
  • TTL Cache: TransactionCache with automatic cleanup ensures memory doesn't grow unbounded.
