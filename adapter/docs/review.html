🚨 Critical Issues

Issue #1: CRITICAL - Dual Lifecycle Management (Race Condition)

Severity: CRITICAL | Location: ShutdownHookManager + AdapterShutdownListener

Problem: Two independent shutdown mechanisms running simultaneously:

  1. ShutdownHookManager (service/ShutdownHookManager.java)
    • @Component (eager initialized)
    • Registers JVM shutdown hook at construction
    • Fires on SIGTERM/SIGINT
    • Calls orchestrator.shutdown()
  2. AdapterShutdownListener (lifecycle/AdapterShutdownListener.java)
    • @Component implementing SmartLifecycle
    • getPhase() = Integer.MAX_VALUE → stops FIRST in Spring sequence
    • Fires on Spring shutdown
    • Also calls orchestrator.shutdown()

Race Condition Scenario:

SCENARIO: Container sends SIGTERM while Spring running ├─ JVM receives SIGTERM ├─ JVM shutdown hook fires IMMEDIATELY │ └─ ShutdownHookManager.run() → orchestrator.shutdown() [FIRST] │ └─ Drains cache, stops threads, closes socket ✓ ├─ Spring also initiates shutdown sequence (concurrent) ├─ AdapterShutdownListener.stop() called [SECOND] │ └─ performPreShutdown() → orchestrator.shutdown() [AGAIN!] │ └─ ✗ Cache already drained │ └─ ✗ Socket already closed → SocketException │ └─ ✗ Threads already terminated └─ Unpredictable behavior, possible data loss

Impact:

  • Double execution of drainResponseCache()
  • Multiple socket.close() calls → exceptions
  • SessionEndNotifier race condition
  • Responses may not be fully flushed to Central

Requirements Violation: REQ-SHUTDOWN-001 requires ordered, single shutdown sequence with known timeout.

Recommendation: REMOVE ShutdownHookManager ENTIRELY. Let Spring's SmartLifecycle handle all shutdown. Spring already provides graceful shutdown hooks; no need for Runtime.addShutdownHook().

Issue #2: HIGH - TcpServer Class Unused (Dead Code)

Severity: HIGH | Location: tcp/TcpServer.java (~90 lines)

Problem:

  • NEVER USED in adapter execution flow
  • @ConditionalOnProperty with matchIfMissing=false (disabled by default)

Recommendation: DELETE ENTIRE CLASS. No legitimate use case in current architecture. If server capability needed later, implement as separate feature.

Issue #3: HIGH - orchestrator.shutdown() Not Idempotent

Severity: HIGH | Location: tcp/AdapterOrchestrator.java:325

Problem: The shutdown method doesn't guard against multiple invocations:

public synchronized void shutdown() throws Exception { if (!running) { logger.warn("Orchestrator not running"); return; // ← Exits early IF running=false } running = false; // But these still execute even if called second time: senderThread.stop(); for (ProcessorThread t : processorThreads) { t.stop(); } drainResponseCache(); // ← Polling on closed socket! sessionEndNotifier.stop(); }

Impact: First shutdown sets running=false properly. Second shutdown returns early, but by then resources are already cleaned. If third+ shutdown occurs in concurrent context, undefined behavior.

Recommendation: Make truly idempotent by checking individual thread states or using AtomicBoolean to compare-and-set:

private static final AtomicBoolean shuttingDown = new AtomicBoolean(false); public synchronized void shutdown() throws Exception { if (!shuttingDown.compareAndSet(false, true)) { logger.info("Shutdown already in progress"); return; } // ... actual shutdown logic ... }

Issue #4: HIGH - SessionManager State Ambiguity

Severity: HIGH | Location: service/SessionManager.java

Problem: Allows state transitions that violate session semantics:

  • State machine allows: PROCESSING → (pauseProcessing) → SESSION_STARTED
  • Can transition BACK to SESSION_STARTED from PROCESSING
  • Pause/resume logic (pauseProcessing(), beginProcessing()) never used
  • Unspecified in requirements how to handle SESSION_END during pause

Requirements Violation: REQ-MSG-001 specifies unidirectional flow: SESSION_START → TRANSACTION* → SESSION_END. No pause/resume defined.

Recommendation: Remove pauseProcessing() and beginProcessing() methods. Simplify to strict state machine: IDLE → SESSION_STARTED → PROCESSING → SESSION_ENDED → IDLE.

Issue #9: MEDIUM - Redundant State Tracking

Location: tcp/AdapterOrchestrator.java + service/SessionManager.java

Multiple state variables tracking same concept:

// In AdapterOrchestrator: private volatile boolean procrHealthy = false; private volatile boolean sessionStarted = false; // In SessionManager: private final AtomicReference<AdapterState> currentState; // Also tracks SESSION_STARTED

Risk of inconsistency if not kept in sync. Two sources of truth for session state.

Recommendation: Centralize state in SessionManager. Remove sessionStarted flag from orchestrator, query SessionManager instead.

Issue #10: MEDIUM - ProcrClient Health Check Timing

Location: http/ProcrClient.java + tcp/AdapterOrchestrator.java:103-135

Health check task runs every 5 seconds, but RestTemplate timeout is 10 seconds. Potential for concurrent health checks:

// Task runs every 5 seconds startProcrHealthCheckTask(5000); // But RestTemplate has 10-second timeout // If check takes 8 seconds, next check fires before previous completes

Recommendation: Use ScheduledExecutorService with fixed delay (wait 5s after completion) instead of fixed rate.
