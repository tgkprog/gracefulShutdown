Adapter Service - Requirements Specification

Project: Transaction Adapter Service
Technology Stack: Java Spring Boot TCP Socket + HTTP
Document Version: 1.0
Last Updated: October 22, 2026

1. Overview

The Adapter service is a Spring Boot application that acts as a bridge between a Central transaction server and a PROCR processor service. Each Adapter instance maintains a single persistent TCP connection to one Central instance, receives transaction messages, transforms them from JSON to YAML format, sends them to PROCR via HTTP, transforms the responses back to JSON format, and sends them back to Central. The Adapter uses a thread pool to handle concurrent transaction processing.

2. High-Level Architecture

Transaction Flow:

Central
  ↓ (TCP: JSON Transaction)
Adapter (Main Thread: Read Messages)
  ↓ (Queue)
Adapter (Thread Pool: Transform & Process)
  ↓ (HTTP POST: YAML)
PROCR (/process endpoint)
  ↓ (HTTP Response: JSON)
Adapter (Main Thread: Transform & Send Back)
  ↓ (TCP: JSON Response)
Central
REQ-ARC-001: Single Central Connection
  • Each Adapter instance maintains exactly ONE persistent TCP connection to ONE Central instance
  • Connection is established at startup or on-demand
  • Connection is reused for all transaction message exchanges
  • If connection is lost, Adapter shall attempt to reconnect
REQ-ARC-002: Thread Pool Architecture
  • Adapter uses a configurable thread pool to process transactions concurrently
  • Main application thread: Reads messages from Central TCP socket
  • Thread Pool threads: Transform messages, call PROCR, transform responses, queue response back to Central
  • Response thread: Sends queued responses back to Central TCP socket

3. Connection Management

REQ-CONN-001: TCP Connection to Central
  • Central Host: Configurable (environment variable or config file)
  • Central Port: Configurable (default: 5000)
  • Connection Mode: Client (Adapter initiates connection to Central)
  • Connection Lifecycle: Persistent until Adapter shutdown or error
REQ-CONN-002: Session Management with Central
  • On connection establishment, Adapter shall wait to receive messages from Central
  • When Adapter starts or after reconnection, it shall automatically send SESSION_START to Central
  • Adapter shall process all transactions until receiving SESSION_END from Central
  • When Adapter receives SESSION_END, it shall continue processing queued transactions
  • Upon graceful shutdown, Adapter shall send SESSION_END to Central if not already received
REQ-CONN-003: Connection Resilience
  • If TCP connection to Central is lost unexpectedly, log the error
  • Attempt to reconnect with exponential backoff (1s, 2s, 4s, 8s... up to max 60s)
  • Upon reconnection, resend SESSION_START to Central
  • Discard all unprocessed transactions from previous session

4. Message Handling

4.1 Inbound Messages from Central (JSON)

REQ-MSG-001: Message Types from Central
Message Type Format Action
TRANSACTION JSON with TXN details Queue for processing via thread pool
SESSION_START Session initiation marker Log and set session state to ACTIVE
SESSION_END Session termination marker Log, set session state to INACTIVE, continue processing queued transactions
REQ-MSG-002: Transaction Message Structure (from Central)
Transactions received from Central in JSON format contain:
{ "txn_id": "TXN-001234", "stan": "123456", "txn_type": "T1", "narration": "Purchase of Office Supplies", "quantity": 5, "rate": 99.99, "taxes": 49.99, "total": 549.89, "timestamp": "2026-10-22T23:17:46.602+05:30" }

4.2 Outbound Messages to Central (JSON)

REQ-MSG-003: Response Message Format (to Central)
Responses sent back to Central in JSON format contain:
{ "txn_id": "TXN-001234", "stan": "123456", "status": "APPROVED", "reason": null, "date": "2026-10-22T23:17:46.602+05:30", "timestamp": "2026-10-22T23:17:46.602+05:30" }
{ "txn_id": "TXN-001235", "stan": "654321", "status": "REJECTED", "reason": "Insufficient Funds", "date": "2026-10-22T23:17:46.602+05:30", "timestamp": "2026-10-22T23:17:46.602+05:30" }

5. Data Transformation

5.1 JSON to YAML Transformation (for PROCR)

REQ-TRANSFORM-001: JSON → YAML Conversion
  • Convert JSON transaction from Central into YAML format
  • All fields shall be preserved as-is
  • No data loss or modification during conversion
  • YAML structure must match PROCR's expected input format
# Input JSON from Central: { "txn_id": "TXN-001234", "stan": "123456", "txn_type": "T1", "narration": "Purchase of Office Supplies", "quantity": 5, "rate": 99.99, "taxes": 49.99, "total": 549.89, "timestamp": "2026-10-22T23:17:46.602+05:30" } # Output YAML for PROCR: txn_id: TXN-001234 stan: "123456" txn_type: T1 narration: Purchase of Office Supplies quantity: 5 rate: 99.99 taxes: 49.99 total: 549.89 timestamp: "2026-10-22T23:17:46.602+05:30"

5.2 YAML to JSON Transformation (from PROCR)

REQ-TRANSFORM-002: YAML → JSON Conversion
  • Convert YAML response from PROCR back to JSON format
  • Add txn_id and stan from original request (echo)
  • Include approval status and rejection reason (if applicable)
  • Include processing timestamp from PROCR response
  • Send to Central in JSON format

6. Request Processing Pipeline

REQ-PROC-001: Thread Pool Processing
  • Thread Pool Size: Configurable (default: 10 threads)
  • Queue Type: Blocking queue (handle backpressure gracefully)
  • Queue Size: Configurable (default: 1000)
  • Each thread processes one transaction at a time
  • Threads execute the following steps in sequence
REQ-PROC-002: Transaction Processing Steps
For each transaction received from Central:
  1. Enqueue transaction to thread pool processing queue
  2. Log transaction receipt (ID, STAN, type)
  3. Convert JSON to YAML format
  4. Make HTTP POST request to PROCR /process endpoint
  5. Parse JSON response from PROCR
  6. Log approval/rejection decision
  7. Transform response to JSON format (if not already)
  8. Enqueue response to outbound queue for transmission to Central
REQ-PROC-003: Response Send-Back Logic
  • Maintain a queue of responses to be sent back to Central
  • Separate thread or main thread sends queued responses via TCP socket
  • Responses sent in order (FIFO) to maintain message sequence
  • Log each response sent to Central

7. PROCR HTTP Integration

REQ-PROCR-001: HTTP Client Configuration
  • PROCR Host: Configurable (environment variable or config file)
  • PROCR Port: Configurable (default: 8080)
  • PROCR Base URL: http://[PROCR_HOST]:[PROCR_PORT]
  • Endpoint: /process
  • HTTP Method: POST
REQ-PROCR-002: HTTP Request Details
  • Content-Type: application/x-yaml
  • Request Body: YAML-formatted transaction
  • Timeout: Configurable (default: 10 seconds)
  • Retry Logic: Retry failed requests (3 attempts with exponential backoff)
  • If all retries fail, log error and treat as rejection (reason: "Service Unavailable")
REQ-PROCR-003: HTTP Response Handling
  • Success (200 OK): Parse JSON response, extract approval status and details
  • Client Error (400): Log error, treat as rejection with reason "Invalid Request"
  • Server Error (500): Log error, retry with backoff
  • Timeout/Connection Error: Retry with exponential backoff

8. Logging and Monitoring

REQ-LOG-001: Event Logging
Log all significant events:
  • Startup: Adapter started, attempting to connect to Central at [HOST:PORT]
  • Connection: Connected to Central, sending SESSION_START
  • Message Receive: Received TXN-[ID] from Central (STAN: [STAN], Type: [TYPE])
  • Thread Pool: Processing TXN-[ID] in thread pool (Queue depth: [N])
  • PROCR Request: Sending TXN-[ID] to PROCR
  • PROCR Response: Received response for TXN-[ID] (Status: APPROVED/REJECTED, Reason: [REASON])
  • Response Send: Sending response for TXN-[ID] back to Central
  • Session End: Received SESSION_END from Central, processing final transactions
  • Disconnection: Lost connection to Central, attempting reconnect
  • Shutdown: Adapter shutting down gracefully
REQ-LOG-002: Log Format
All logs include:
  • Timestamp (ISO 8601)
  • Log Level (INFO, WARN, ERROR)
  • Component/Class name
  • Descriptive message with context
[2026-10-22T23:17:46.602+05:30] INFO AdapterService - Received TXN-001234 from Central (STAN: 123456) [2026-10-22T23:17:46.603+05:30] INFO TransactionProcessor - Processing TXN-001234 (Queue: 5) [2026-10-22T23:17:46.650+05:30] INFO ProcRClient - TXN-001234 APPROVED (47ms) [2026-10-22T23:17:46.651+05:30] INFO AdapterService - Sending response for TXN-001234 to Central
REQ-LOG-003: Performance Metrics (optional)
  • Track request latency (end-to-end time from Central to PROCR and back)
  • Track PROCR response time
  • Track thread pool queue depth
  • Log metrics periodically (every 60 seconds) or on request

10. Error Handling

REQ-ERR-001: Central Connection Loss
  • If TCP connection to Central is lost, log error immediately
  • Attempt to reconnect with exponential backoff
  • Discard pending transactions from previous session
  • Upon successful reconnection, send SESSION_START and resume processing
REQ-ERR-002: PROCR Unavailable
  • If PROCR is unavailable, retry HTTP request with exponential backoff
  • After max retries, treat as rejection with reason "Service Unavailable"
  • Log warning with transaction details
  • Send negative response back to Central
REQ-ERR-003: Invalid Messages
  • If received message from Central is malformed JSON, log error and skip
  • If PROCR response is malformed JSON, log error and treat as rejection
  • Do not crash the Adapter; continue processing subsequent messages
REQ-ERR-004: Thread Pool Overflow
  • If thread pool queue is full, log warning
  • Blocking queue will block reads from Central until space is available
  • This provides natural backpressure (Central will stop sending if Adapter can't process)

11. Graceful Shutdown

REQ-SHUTDOWN-001: Graceful Shutdown Procedure
Upon receiving SIGTERM or shutdown signal:
  • Stop accepting new messages from Central
  • Allow thread pool to complete processing of queued transactions
  • Send all queued responses back to Central
  • Send SESSION_END to Central (if not already received)
  • Close TCP connection to Central gracefully
  • Flush all logs
  • Exit application with status code 0
REQ-SHUTDOWN-002: Shutdown Timeout
  • Allow up to 30 seconds for graceful shutdown
  • After timeout, force shutdown thread pool and close connections
  • Log any unprocessed transactions before shutdown

12. Performance Requirements

REQ-PERF-001: Throughput
  • Adapter shall handle at least 100 concurrent transactions in the thread pool
  • End-to-end latency (Central to PROCR and back): <500ms for 95th percentile
  • PROCR response time typically <200ms, so bottleneck is network and queuing
REQ-PERF-002: Memory Efficiency
  • Thread pool of 10 threads should use minimal memory
  • Queued transactions held in memory temporarily
  • No long-term storage; queues cleared on shutdown or Central disconnection

13. State Machine

Adapter State Transitions:

STARTING
└─ (Attempting to connect to Central)
    ↓
CONNECTED (Waiting for SESSION_START or receiving transactions)
└─ (Received SESSION_START)
    ↓
ACTIVE (Processing transactions, sending responses)
└─ (Received SESSION_END)
    ↓
DRAINING (Processing final queued transactions, sending responses)
└─ (All queued transactions processed)
    ↓
IDLE (Ready for new SESSION_START)
└─ (Connection lost or shutdown signal)
    ↓
SHUTDOWN (Graceful shutdown, closing connections)

14. Summary

Aspect Details
Central Connection 1 persistent TCP connection (client mode)
Thread Pool Configurable size (default: 10), processes transactions concurrently
Data Transformation JSON ↔ YAML bidirectional conversion
PROCR Integration HTTP POST to /process endpoint, handle retries and errors
Logging Comprehensive event logging, performance metrics optional
Resilience Reconnection logic, retry logic, graceful degradation
Shutdown Graceful shutdown with transaction draining (30s timeout)
Key Implementation Points:
  • Separate thread for reading from Central (blocking I/O)
  • Thread pool for processing transactions concurrently
  • Response queue and thread for sending back to Central
  • Use Spring Boot's RestTemplate or HttpClient for HTTP calls
  • Use Jackson for JSON/YAML serialization
  • Implement circuit breaker pattern for PROCR failures (optional)
  • Log everything; include thread context in logs for debugging
